# Changelog

All notable changes to this project are documented here, in reverse-chronological order. Add an entry each time a roadmap slice ships (see ROADMAP.md).

Format per entry: date, roadmap slice / FR reference, one-line description, verification status.

## [Unreleased]
- **2026-08-21 — N/A relabeled to "None Found" (display copy only):** After delete (FR-017) shipped, Sapna flagged that "N/A" no longer read as clearly distinct from permanent removal — both could sound like "get rid of it." Discussed a few alternatives and landed on **"None Found"**, which reads as a reversible triage call ("I looked, it's not here") rather than "this doesn't belong here," matching the actual FR-014-reversible semantics. Changed `ITEM_STATUS_LABELS.na` in `app.js` and the zone-detail hint text in `index.html`; the internal status value stays `na` (no data migration, no other code path touched). Bumped service worker `CACHE_NAME` to v8. PRD.md FR-004 updated with an open-questions note documenting the rename. **Verified in-browser:** item row and zone-detail hint text both render "None Found" after cycling an item through the status sequence. **Confirmed working on Sapna's actual installed iPhone app (2026-08-21).**
- **2026-08-21 — Delete item (post-M2.3, not an FR — Sapna requested it directly):** Sapna wanted a way to permanently remove an unwanted item from a zone's checklist, distinct from marking it N/A (FR-004's "doesn't apply, handled differently" state, which is reversible via FR-014 and keeps the item visible). PRD.md has no FR for item deletion — flagged and confirmed with Sapna rather than assumed: (1) delete applies to **any** item, template or custom, not just user-added ones; (2) deletion is irreversible (no undo, unlike N/A), so it requires a confirm prompt first. Added a "✕" delete button next to each item's status-cycle button in the zone detail view (`removeItem()` in `app.js`, using the existing `deleteItem()` helper in `data.js` — built in M1.1, never wired to UI until now). `confirm()` gates the actual delete; canceling leaves the item untouched. Bumped service worker `CACHE_NAME` to v7. **Verified in-browser**: delete removes the item and persists after reload with correct % resolved recalculation (confirmed via direct function calls with `window.confirm` stubbed true/false, since the automation tool auto-dismisses native `confirm()` dialogs as Cancel — which itself confirmed the cancel path correctly leaves data untouched). Works on both template and custom items. **Confirmed working on Sapna's actual installed iPhone app (2026-08-21)**, including the native `confirm()` dialog reading fine on iOS Safari.
- **2026-08-21 — M2.3 (Add custom item, FR-005):** Zone detail now has an "Add an item" input + Add button below the checklist (`addCustomItem()` in `app.js`, using the existing `addItem()` helper in `data.js` — no data-layer change needed). New items are created with `source: 'custom'` and `status: 'pending'`, identical shape to template items, so they get the same status-cycle button, icons, and styling as FR-004 with no special-casing. Blank/whitespace-only input is a no-op (guarded, doesn't create an empty item). Adding an item to a not-started zone also bumps it to in_progress, same as the first item-status interaction (FR-011 status accuracy). Bumped service worker `CACHE_NAME` to v6. **Verified in-browser** via the project's `dev-server` launch config (after clearing a stale service-worker cache that was serving the pre-edit page — a repeat of the known GitHub Pages/SW caching gotcha, see TECHNICAL_DESIGN.md): added a custom item via the Add button, confirmed it renders as Pending with the same icon/styling as template items, cycled it to Dealt With via the same tap-to-cycle interaction as FR-004, confirmed persistence and correct % resolved recalculation after a full page reload (1/9 → 11%), and confirmed the empty-input guard blocks blank submissions. Enter-key submission (same pattern as the existing zone-name-input) is implemented but not exercised by the automation tool due to a synthetic-keyevent limitation — code-identical to the already-verified zone-name-input pattern. **Confirmed working on Sapna's actual installed iPhone app (2026-08-21).**
- **2026-08-20 — M2.2 (Item status cycle, FR-004):** Zone detail items are now tappable buttons that cycle Pending → Dealt With → N/A → Pending (`cycleItemStatus()` in `app.js`, using `updateItem()` from `data.js`). Each state gets distinct visual treatment: Dealt With shows a checkmark, strikethrough, and teal/green accent; N/A shows a dash icon and reduced opacity with no strikethrough — a lighter acknowledgment than Dealt With, so it doesn't read as a dead click but stays clearly less "celebratory." **Open question resolved with Sapna (2026-08-20):** confirmed N/A should get this lightweight acknowledgment rather than staying silent. First item interaction on a zone also bumps its status from Not Started to In Progress (needed so FR-011's zone-list status stays accurate now that items are interactive — not itself an FR-004 requirement). XP awarding on Dealt With (part of FR-004's acceptance criteria) is deliberately deferred to M3.3 (FR-007), since the fixed per-item XP value hasn't been set yet; `xpAwarded` stays 0 for now. Bumped service worker `CACHE_NAME` to v5. **Verified in-browser** via the project's `dev-server` launch config: full Pending→Dealt With→N/A→Pending cycle confirmed via DOM class + computed-style checks (N/A: opacity 0.6, no strikethrough vs. Dealt With: strikethrough + teal), zone list correctly reflects updated status (Not Started → In Progress) and recalculated % resolved (2/7 items → 29%) both immediately and after a full page reload (confirming localStorage persistence), and the zero-item empty state still renders correctly. **Confirmed working on Sapna's actual installed iPhone app (2026-08-20).**
- **2026-08-20 — M0.3 (Manual data export/import, FR-016):** Added `exportDataJson()`/`importDataJson()` to `data.js` and wired an "Export Data" / "Import Data" section into the zone list screen (`index.html`/`app.js`). Export downloads the full data blob as a timestamped JSON file. Import reads a chosen file, warns via `confirm()` before overwriting existing data (only when zones already exist), and validates the file has the expected `{zones, items, rewards, weeklyCheckins}` array shape before writing — malformed JSON or wrong-shaped files are rejected with an on-screen message and existing data is left untouched. Bundled a best-effort `navigator.storage.persist()` call on boot (not load-bearing, per FR-016). Bumped service worker `CACHE_NAME` to v4. **Verified two ways:** (1) direct console invocation (`exportDataJson`/`importDataJson`) confirming valid export → re-import round-trips data correctly and malformed/wrong-shape JSON is rejected without touching existing data; (2) **real on-device pass by Sapna** over the local network (phone Safari hitting the dev server via LAN IP) — exported real data as a backup, downloaded a deliberately different test JSON file, imported it and confirmed the zone list updated to match that file's content exactly (proving Import reads and applies the selected file, not a no-op), then re-imported the original backup and confirmed real data was restored. Confirms the full button → file picker → import UI path works, not just the underlying functions. Also surfaced and diagnosed (not a regression): `crypto.randomUUID()`, used for all new zone/item IDs, requires a secure context (HTTPS or `localhost`) and is unavailable when testing over a plain-HTTP LAN IP — doesn't affect the real deployed app (always HTTPS) or `localhost` dev testing, only local-network-IP testing of zone/item *creation*; left unfixed per Sapna's call, since it's a testing-method limitation, not a product bug. This retroactively satisfies the M0.3 gate flagged 2026-08-20 — M2.2 onward can now proceed.
